## 一：APIFOX 的使用

### 教学目标

- 理解 API 是什么，前后端如何通过接口通信
- 掌握 APIFOX 的基本操作：新建请求、设置参数、查看响应
- 学会用 APIFOX 调试接口、生成 Mock 数据
- 理解接口文档的作用，培养前后端协作意识

### 知识点讲解

#### 1. 什么是 API？

API（Application Programming Interface）是前后端之间的"合同"。前端不需要知道后端怎么实现，只需要按照约定好的格式发送请求，就能拿到数据。

```
前端                    后端
  |  GET /api/users      |
  | -------------------> |
  |  { data: [...] }     |
  | <------------------- |
```

#### 2. HTTP 请求的基本结构

```
请求方法   URL                   请求头
GET       /api/articles?page=1   Authorization: Bearer <token>

请求体（POST/PUT 时使用）
{
  "title": "文章标题",
  "content": "内容..."
}
```

常用请求方法：

- `GET` — 获取数据（查）
- `POST` — 创建数据（增）
- `PUT` / `PATCH` — 更新数据（改）
- `DELETE` — 删除数据（删）

#### 3. HTTP 状态码

| 状态码 | 含义                          |
| ------ | ----------------------------- |
| 200    | 成功                          |
| 201    | 创建成功                      |
| 400    | 请求参数有误（客户端问题）    |
| 401    | 未认证（没登录或 Token 过期） |
| 403    | 无权限                        |
| 404    | 资源不存在                    |
| 500    | 服务器内部错误                |

#### 4. APIFOX 核心功能介绍

**界面区域说明：**

```
左侧：项目/接口目录树
中间：接口详情（请求配置）
右侧：响应结果
```

**四个核心操作：**

1. **新建接口**：填写方法、URL、参数描述，保存为团队文档
2. **调试请求**：填入参数后点击"发送"，查看真实响应
3. **Mock 数据**：后端未开发完时，前端可用 Mock 服务生成假数据
4. **环境变量**：统一管理开发/测试/生产环境的 base URL 和 Token

#### 5. APIFOX 中的环境变量

在实际项目中，同一个接口在不同环境下 URL 不同：

- 开发环境：`http://localhost:3000`
- 测试环境：`http://test.example.com`
- 生产环境：`https://api.example.com`

通过"环境变量"功能，只需切换环境，所有请求自动使用对应的 base URL，避免手动修改。

**常用变量示例：**

```
BASE_URL = http://localhost:3000
TOKEN    = eyJhbGciOiJIUzI1NiJ9...
```

在请求 URL 中写 `{{BASE_URL}}/api/users`，请求头写 `Bearer {{TOKEN}}`。

#### 6. Mock 数据功能

当后端接口还没写好时，APIFOX 可以根据接口定义自动生成 Mock 数据，让前端不被后端阻塞。

Mock 规则示例（在 APIFOX 的响应 Schema 中定义）：

```json
{
  "code": 200,
  "data": {
    "list|10": [{
      "id|+1": 1,
      "title": "@ctitle(5,20)",
      "author": "@cname",
      "createdAt": "@datetime"
    }],
    "total": 100
  }
}
```

### 课堂演示步骤

1. 打开 APIFOX，新建一个项目"暑期培训练习"
2. 新建接口：`GET /api/articles` — 获取文章列表
3. 添加 Query 参数：`page`（number）、`pageSize`（number）
4. 定义响应结构，开启 Mock
5. 在调试 Tab 发送请求，看 Mock 返回的假数据
6. 演示环境变量：新建"开发环境"，添加 `BASE_URL` 变量

## 二：分页器的实现

### 目标

- 理解分页的业务逻辑：为什么需要分页，前后端各做什么
- 掌握分页参数的计算方式
- 能手写一个功能完整的分页组件
- 能将分页组件与真实/Mock 接口对接

### 知识点讲解

#### 1. 为什么需要分页？

如果一次性返回所有数据：

- 数据库压力大
- 网络传输慢
- 页面渲染卡顿

分页让每次请求只返回一小部分数据。

#### 2. 分页的两种方式

**方式一：Offset 分页（最常见）**

```
请求参数：page=2, pageSize=10
后端 SQL：SELECT * FROM articles LIMIT 10 OFFSET 10
```

| 参数       | 说明                    |
| ---------- | ----------------------- |
| `page`     | 当前页码，从 1 开始     |
| `pageSize` | 每页条数，通常 10 或 20 |
| `total`    | 后端返回的总条数        |

**方式二：Cursor 分页**（适合无限滚动，暂不深入）

#### 3. 核心计算公式

```js
// 总页数
const totalPages = Math.ceil(total / pageSize)

// 是否有上一页
const hasPrev = currentPage > 1

// 是否有下一页
const hasNext = currentPage < totalPages

// 某页的数据偏移量（给后端用）
const offset = (currentPage - 1) * pageSize
```

#### 4. 分页器 UI 的页码渲染策略

当总页数很多时，不能把所有页码都显示出来，需要用省略号（`...`）截断。

常见规则：

- 始终显示第 1 页和最后一页
- 当前页前后各显示 2 页
- 其余用 `...` 代替

```
示例（当前页 = 6，总页数 = 20）：
1 ... 4 5 [6] 7 8 ... 20
```

实现这个逻辑的函数见 `practice/02-pagination/pagination.js`。

#### 5. 与接口对接

```js
async function loadArticles(page) {
  const res = await fetch(`/api/articles?page=${page}&pageSize=10`)
  const json = await res.json()
  renderList(json.data.list)
  renderPaginator(page, json.data.total, 10)
}
```

**注意事项：**

- 切换页码时要有加载状态（loading），防止用户连续点击
- 请求失败时要有错误提示
- URL 里最好同步页码（`?page=2`），方便分享链接

## 三：登录状态保持

### 教学目标

- 理解为什么 HTTP 是无状态的，以及这带来的问题
- 掌握 Token（JWT）认证流程
- 理解 Cookie vs localStorage vs sessionStorage 的区别
- 能实现：登录 → 保存 Token → 携带 Token 发请求 → 退出登录

### 知识点讲解

#### 1. HTTP 无状态问题

HTTP 协议本身不记录"谁发的请求"。每次请求对服务器来说都是全新的陌生人。

```
你：GET /api/my-profile
服务器：你是谁？
你：上次你告诉我我是张三啊
服务器：我不记得
```

解决方案：在每次请求中主动带上"身份证明"。

#### 2. Token 认证流程（JWT）

```
1. 登录
   前端发送: POST /api/login  { username, password }
   后端验证成功后返回: { token: "eyJ..." }

2. 保存 Token
   前端把 token 存入 localStorage 或 Cookie

3. 后续请求携带 Token
   请求头加上: Authorization: Bearer eyJ...

4. 后端验证
   每次请求，后端解析 Header 中的 Token，确认用户身份
```

#### 3. JWT 的结构

JWT（JSON Web Token）由三部分组成，用 `.` 分隔：

```
eyJhbGciOiJIUzI1NiJ9   <- Header（算法信息，Base64）
.eyJ1c2VySWQiOjF9      <- Payload（用户数据，Base64）
.SflKxwRJSMeKKF2QT4fwp <- Signature（签名，防篡改）
```

Payload 可以包含：

```json
{
  "userId": 1,
  "username": "张三",
  "exp": 1721000000
}
```

> **重要**：JWT 的 Payload 是 Base64 编码，不是加密！不要在里面存密码等敏感信息。

#### 4. 存储方式对比

| 存储方式            | 持久性           | 容量 | 安全性              | 适用场景   |
| ------------------- | ---------------- | ---- | ------------------- | ---------- |
| `localStorage`      | 永久（手动清除） | ~5MB | 易被 XSS 攻击读取   | 记住登录   |
| `sessionStorage`    | 标签页关闭即清除 | ~5MB | 同上                | 临时会话   |
| `Cookie` (httpOnly) | 可设置过期时间   | ~4KB | httpOnly 防 JS 读取 | 高安全需求 |

课程中使用 `localStorage`，简单易懂。生产环境推荐 `httpOnly Cookie`。

#### 5. 路由守卫

登录保护的核心：在跳转到需要登录的页面前，检查是否有 Token。

```js
function checkAuth() {
  const token = localStorage.getItem('token')
  if (!token) {
    window.location.href = '/login.html'
    return false
  }
  return true
}
```

#### 6. Token 过期处理

Token 通常有过期时间。过期后，后端会返回 `401 Unauthorized`。

前端应在请求拦截器中统一处理：

```js
if (response.status === 401) {
  localStorage.removeItem('token')
  window.location.href = '/login.html'
}
```

#### 7. 退出登录

```js
function logout() {
  localStorage.removeItem('token')
  window.location.href = '/login.html'
}
```
